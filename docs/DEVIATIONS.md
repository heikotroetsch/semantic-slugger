| 22  | M1.5      | 13.2, 13.4, 13.6 | Tail lag fix. In tiers B and C, when all `maxAttempts` indexes from `k = n` are taken at tail length `t`, the tail grows to `t + 1` and the scan starts again at `k = n`, up to the room left (`L - len(body) - sep`). `ExhaustedError.details.tries` counts every try over all lengths. Implemented in the empty path (`src/core/empty.ts`); the M5 resolver (13.4) must use the same rule. Exact mode and opaque IDs have one length only, so they are unchanged.                                                                                                                                                                                                     | The start index `k = countBody(n)` assumes indexes below `n` hold the rows. Every hash collision between two tails of one length moves the used indexes one step ahead of `n`, for good. At `t = 3` (15,680 tails, used for `n` = 35..979) about `n^2 / (2K)` collisions build up, so near `n = 500` the 8-attempt window holds only taken IDs and every later row throws (seen: row 510 of 3000 empty titles in max mode). The 13.4 estimate "about 2e-10 chance to exhaust" ignores this build-up. A new tail length is a fresh space, and the result stays deterministic for the same store state. Regression test: 3000 identical titles, tier B, max mode. |
